# 通知文案

每条推送给你的消息长什么样、为什么只用这几种写法。文案出处是 `messages.py`（文字）与`render.py`（版式），**正文样例由 `render_event()` 真实渲染**（ActionCard 那段的账号与标题换成了另一组假数据，结构一致）——手抄的样例迟早和代码不一致。

## 版式：只用两边都支持的元素

钉钉与企业微信**共用同一个 `markdown` 字段**，所以版式取两者的**交集**：

| 元素                                     | 钉钉 | 企业微信 markdown            |
| ---------------------------------------- | :--: | ---------------------------- |
| `###` 标题                               |  ✅  | ✅（`#` 与文字之间要有空格） |
| `**加粗**`                               |  ✅  | ✅                           |
| `[文字](链接)`                           |  ✅  | ✅                           |
| `>` 引用                                 |  ✅  | ✅                           |
| `- ` 无序列表                            |  ✅  | ✗（原样显示 `- `）— **正文不用**；只有钉钉 ActionCard 的正文用，见下方「钉钉里的新作品」 |
| 表格 / 代码块 / 行内代码 / 分隔线 / 斜体 |  ✗   | ✗                            |

**每个字段写成 `**标签**：值`，自成一段，段与段之间空一行，不用列表圆点。** 标签加粗是唯一的强调手段——`**` 是交集里唯一两边都认的语法，值本身不做任何装饰（不加粗、不套行内代码）。分行靠的是**空行**：钉钉把单个换行当**软换行**折叠，相邻两行只隔一个换行会被挤成一整行（第一版“推送内容太乱”的根因）；而被空行隔开的段落，钉钉与企业微信都会渲染成独立的行，不依赖行尾那些看不见、传输一次就可能丢的空格。

| 约束                    | 值                 | 为什么                                                                                                       |
| ----------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------ |
| 正文上限                | 3500 字节（UTF-8） | 企业微信 markdown 硬上限 4096 字节，超了整条消息发不出去；超长时按**行边界**截断并附一句说明                 |
| 单条作品标题            | 80 字符            | 抖音标题可以很长，整段塞进来会淹掉其它字段；面板与事件表里仍是全文。**先截断再转义**，否则会切出落单的反斜杠 |
| 通知栏标题（`subject`） | 单行纯文本         | 钉钉的 `title`、Bark 标题、Server 酱标题都不做 markdown 解析，所以这里不转义、也不留标记                     |
| 列表条数                | 最多 10 条         | 其余折成一句「…另有 N 条」                                                                                   |

## 各渠道拿到的是哪一份

一条消息渲染一次、三种形态，各渠道各取所需：

| 渠道             | 用到的字段                      | 说明                                                                                                       |
| ---------------- | ------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 钉钉群机器人     | `markdown` + `title`(=subject)；新作品用 ActionCard（`btns` 一个按钮） | 本页的版式规则就是为它定的；新作品见下一节                                                  |
| 企业微信群机器人 | `markdown`                      | 与钉钉共用版式（不含封面图，企业微信 markdown 不支持图片）                                                  |
| Server 酱        | `markdown` + 标题               | 官方标题上限 **32 字节**，本地按 UTF-8 字节安全截断（一个汉字 3 字节——按字符切等于没切，而且会切出半个字） |
| Bark             | `text` + `subject`              | 纯文本：标题前缀去掉、`**` 去掉、链接展开成 `文字 <url>`                                                   |
| Telegram         | `text`                          | 同上（不带 `parse_mode`，传 markdown 会显示成源码）                                                        |
| 通用 webhook     | `subject` / `text` / `markdown` | 三份都给，接收方自己挑                                                                                     |

::: info "发成功了"是怎么判的
这些渠道**业务失败时也回 HTTP 200**（钉钉与企业微信的 `errcode`、Server 酱与 Bark 的 `code`），
只看状态码就会把"根本没发出去"记成"已送达"——`test-notify` 的 ✓、`delivery_json` 与退出码会一起说谎。
所以每个渠道还会读一遍业务码（钉钉/企业微信 `errcode == 0`、Server 酱 `code == 0`、
Bark `code == 200`、Telegram `ok == true`）；
**响应里没有这个字段时按成功处理**，自建反代之类不按官方格式回包的不会被误判。

Telegram 用 `ok` 是有依据的：官方文档只规定"请求不成功时 `ok` 为 False 并给出 `error_code`"，
**没有规定 HTTP 状态码**（实测假 token 回的是 401，但那是观察结果、不是 API 的保证），
所以判据取它自己定义的那个字段，而不是我们恰好见到过的状态码。
:::

## 会推送的事件（12 种）

下面每段代码块里的内容就是实际发出去的消息；`### ` 那一行去掉 `### ` 就是通知栏标题。

## 钉钉里的“新作品”：独立跳转 ActionCard

新作品在钉钉里不发 markdown，而是发一张**独立跳转 ActionCard**（`msgtype: actionCard` +
`btns` 数组 + `btnOrientation: "0"`，见钉钉「消息发送与接收类型」的 ActionCard 一节）：
**标题带昵称**，正文是字段列表 + 封面，底部一个「点击观看」按钮跳到作品页。
通知栏标题仍是下面的 `【新作品】…`。

```markdown
### 阿Z想开了 发布了新视频

- **标题**：好Q弹的猪鼻子
- **发布时间**：2026-11-10 18:24:00
- **检测时间**：2026-11-10 18:25:03

![封面](https://p3-pc-sign.douyinpic.com/cover.jpeg)
```

按钮：**点击观看** → 作品链接（没有链接时，视频按 id 拼 `https://www.douyin.com/video/<id>`；
图文拼不出可靠地址，就退回普通 markdown）。

几点要知道：

- **标题必须带昵称**：群里会连着滚多条卡片，只写「新视频发布」看不出是谁发的。昵称进了
  标题，正文就不再重复一行「用户」——三个字段刚好。
- **正文可以用 `- ` 列表**：`card_markdown` 只有钉钉会读，不受“钉钉 ∩ 企业微信”的约束，
  所以字段收在同一个列表块里，比每行之间空一行紧凑得多。
- 用 `btns`（独立跳转）而不是 `singleTitle`/`singleURL`（整体跳转）：整块可点的卡片看不出
  哪里能点，一个明确的按钮才是动作位。`btnOrientation: "0"` 是竖排，与 `sampleActionCard2`
  那类“正文 + 竖向按钮”的形态一致。
- 新作品不 @ 人：`AT_MOBILES` 只对告警类通知（作品消失、监控异常、上游异常等）生效，
  所以新作品始终是这张卡片。
- 卡片只放这几项；类型、时长、点赞数、话题、距上次发布只出现在下面的 markdown 版里
  （企业微信、Telegram 等其它渠道）。

### `new_post` —— 作者刚发布的这一条

**通知栏标题**：【新作品】ζωευώ 发布了新视频

```markdown
### 【新作品】ζωευώ 发布了新视频

**标题**：期待让人越来越沉溺 谁和我一样 等不到她的谁

**类型**：视频

**发布**：2026-09-19 16:20（距上次发布 55 天 7 小时）

**时长**：00:38

**数据**：点赞 46.3万 · 评论 1.7万 · 收藏 4.3万 · 分享 27.4万

**话题**：#阿Z想开了

[查看封面图](https://p3-pc-sign.douyinpic.com/cover.jpeg)

[打开作品](https://www.douyin.com/video/7496063824002403638)
```


### `title_changed` —— 作者改了标题（发完再补话题标签是常态）

**通知栏标题**：【标题变更】ζωευώ 的作品换了标题

```markdown
### 【标题变更】ζωευώ 的作品换了标题

**原标题**：旧标题

**新标题**：期待让人越来越沉溺 谁和我一样
```

### `gap_detected` —— 两次观测之间出现没见过的作品区间

**通知栏标题**：【可能漏检】ζωευώ 的更新节奏超过单页窗口

```markdown
### 【可能漏检】ζωευώ 的更新节奏超过单页窗口

**本页最旧作品**：2026-09-19 16:20

**上轮见到的最新作品**：2026-09-17 16:20

> 两次观测之间出现了没见过的作品区间：该账号单次发布数超过了一页窗口，超出部分不会被采集到。建议调大 FETCH_COUNT（当前 15，上限 50）。
```

### `never_seen` —— 最常见的原因是 sec_user_id 写错了

**通知栏标题**：【账号始终无作品】ζωευώ 需要核实 ID

```markdown
### 【账号始终无作品】ζωευώ 需要核实 ID

**账号**：MS4wLjABAAAA4MjT

**已出现轮次**：3

> 该账号从未返回过任何作品。最常见的原因是 sec_user_id 写错了（形态合法但不存在的 ID 会返回 200 + 空列表，上游不会报错）；也可能是账号确实没有作品、或作品全部设为私密。
```

### `all_gone` —— 整批作品在同一时间段内不见，比逐条消失更需要核实

**通知栏标题**：【作品全部消失】ζωευώ 的全部作品同时不见了

```markdown
### 【作品全部消失】ζωευώ 的全部作品同时不见了

期待让人越来越沉溺 · 2026-09-19 16:20

> 该账号的全部作品在同一时间段内消失。如果账号实际仍有作品，可能是上游返回了空列表（接口异常/风控）或作者把作品设为私密，请核实后再处理。
```

### `account_failed` —— 该账号连续失败到阈值

**通知栏标题**：【监控异常】ζωευώ 连续失败 5 次

```markdown
### 【监控异常】ζωευώ 连续失败 5 次

**错误码**：FORBIDDEN\_SCOPE

**详情**：requester does not have scope douyin:read

> 这是配置问题而不是网络问题：FORBIDDEN\_SCOPE —— 修好之前每个账号都会一直失败。
```

### `account_recovered` —— 此前连续失败的账号本轮读成功了

**通知栏标题**：【已恢复】ζωευώ 的监控恢复正常

```markdown
### 【已恢复】ζωευώ 的监控恢复正常

此前连续失败 5 次，本轮已成功读取
```

### `stale_no_update` —— 一次性提醒，发布新作品后重新计时

**通知栏标题**：【长期无更新】ζωευώ 已 14 天没有新作品

```markdown
### 【长期无更新】ζωευώ 已 14 天没有新作品

只提醒一次，该账号发布新作品后重新计时
```

### `upstream_degraded` —— DTK 实例或网络的问题，与某个账号无关

**通知栏标题**：【上游异常】DTK 实例需要处理

```markdown
### 【上游异常】DTK 实例需要处理

**错误码**：upstream\_unreachable

**已出现轮次**：4

**影响**：全局闸门关闭 600 秒，本轮整体跳过

> 上游整体不可用，这与某个账号无关。
```

### `self_degraded` —— dywatch 自己的状态库/磁盘出问题

**通知栏标题**：【自身降级】dywatch 运行环境出了问题

```markdown
### 【自身降级】dywatch 运行环境出了问题

**原因**：状态库所在磁盘空间不足

**详情**：剩余 120 MB，低于阈值 200 MB（SELF_CHECK_FREE_MB）

> dywatch 仍在运行（这条通知就是它发的），但状态库一旦写不进去，作品变化就无法记录。请尽快处理。
```

原因有三种：`disk_low`（磁盘空间低于 `SELF_CHECK_FREE_MB`，上面的样例）、`data_dir_read_only`
（数据目录不可写）、`state_store_write_failed`（状态库写入失败）。这条通知本身就是 dywatch 发的，
所以**推送并没有停**。

## 只落库、不推送的事件（3 种）

这些事件**不进推送通道**，只写事件表（面板的「最近事件」里能看到）。它们要么是窗口挪动的机械后果，要么根本不需要你做任何动作：

| `kind`         | 为什么不推                                       |
| -------------- | ------------------------------------------------ |
| `scrolled_out` | 被新作品挤出单页窗口的机械后果，不是作者删了     |
| `trimmed`      | 超过 `KNOWN_IDS_MAX` 的裁剪，同上                |
| `initialized`  | 账号第一次被记录，否则新上线账号会被历史作品刷屏 |

## 渠道自测（`dywatch test-notify`）

手动验证渠道是否通的那条消息，也走同一套版式：

```markdown
### 【测试】dywatch 通知渠道自检

如果你看到这条消息，说明该渠道可用。
```

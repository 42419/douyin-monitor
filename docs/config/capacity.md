# 容量估算

## 请求速率与覆盖延迟

节奏由 `pacer.py` 决定，**与账号数无关**：

```
请求速率上限 ≈ 60 / 平均(3, 8) ≈ 10.9 次/分钟
轮次周期     ≈ 账号数 × 5.5 秒 + random(15, 40) 秒
```

| 账号数 | 一轮耗时（估） | 请求速率 | 单账号多久被查一次 |
| ------ | -------------- | -------- | ------------------- |
| 5      | ~55 秒         | ~11/min  | ~1 分钟              |
| 10     | ~82 秒         | ~11/min  | ~1.5 分钟            |
| 20     | ~2.3 分钟      | ~11/min  | ~2.5 分钟            |
| 50     | ~5 分钟        | ~11/min  | ~5 分钟              |
| 100    | ~9.6 分钟      | ~11/min  | ~10 分钟             |

约 11 次/分钟远低于 DTK 默认的 120/分钟，对身份池也很温和。**真正的约束是覆盖
延迟**：账号越多，单个账号被检查的间隔越长。如果需要更快的覆盖，权衡点在
`REQUEST_INTERVAL_MIN` / `MAX`（见[配置参考](/config/reference)），但这套数值
是沿用旧项目跑了数月的实测值，调小前建议先想清楚风控代价。

## 状态库会长多大

一轮写一行 `rounds`、只在有事件时写 `events`，所以增长的几乎只有轮次表：

| 账号数 | 每天轮数 | `ROUNDS_KEEP_DAYS=5`（默认） | `=30`      |
| ------ | -------- | ------------------------------ | ---------- |
| 1      | ~2600    | ~1.3 万行                      | ~7.8 万行  |
| 5      | ~1500    | ~7.5 千行                      | ~4.5 万行  |
| 20     | ~630     | ~3.2 千行                      | ~1.9 万行  |

单行很小（9 个字段 + 一个 `ts` 索引），所以几万行也不过几 MB 到十几 MB——问题
不在磁盘，而在这张表**没有任何读取方**（面板与 `dywatch status` 都不看它，只有
排障时手工查），留着几十万行没有意义，所以默认只留 5 天。

调大 `ROUNDS_KEEP_DAYS` 后**下一轮**就会删掉超期行，但 SQLite 删行不缩文件，
要真正回收磁盘空间得停服务后手动 `VACUUM`：

```bash
sqlite3 data/dywatch.db "VACUUM"
```

见[排障](/operations/troubleshooting)中 `rounds` 表太大/太旧的条目。

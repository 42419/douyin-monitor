# 判定规则

## 新作品

本页出现、本地没记录过、也不在 tombstone（已消失记录）里 → 推送。首次见到一个
账号时只记录**不推送**（否则上线一个新账号会被历史作品刷屏）。

## 作品消失（分级确认）

| 类型             | 连续几轮不在本页才确认    |
| ---------------- | ------------------------- |
| 普通作品         | 2（`DELETE_CONFIRM_ROUNDS`） |
| 置顶作品         | 3（`DELETE_CONFIRM_ROUNDS_TOP`） |
| 全部作品同时消失 | 3（`DELETE_CONFIRM_ROUNDS_ALL`，并在通知里附核实提醒） |

确认前只累计计数，不发任何通知；中途回来则计数清零。

**"被新作品挤出窗口"不算消失**：窗口整体前移了多少，就最多有多少条能用挤出解释，
这些走静默清理并写 tombstone——于是它们将来若因窗口回移重新出现，也不会被当成
新作品重复推送（对应事件类型 `scrolled_out`）。

## 漏检

抖音接口返回的是 `count + 本页置顶数` 条，所以"条数达到 count"不等于被截断。
dywatch 改用**时间连续性**判断：本页**非置顶**作品里最旧的发布时间，比上一轮
非置顶作品里最新的发布时间还新 → 中间必然有没采集到的作品，于是告警建议调大
`FETCH_COUNT`（对应事件 `gap_detected`）。

## 游客视角的隐藏问题

漏检针对的是"翻页翻漏了"，还有一类更麻烦的情况：**新作品从发布起就一直不在
游客身份能看到的列表里**——不是接口报错，是一次完整成功的响应，只是内容缺了
一块（抖音对访客身份的主页展示有限制）。这跟上面的"抖动误判"是两类问题：
抖动是"这次看不到、下次能看到"，这个是"只要还用游客身份，可能永远看不到"。

默认情况下 dywatch 对这个问题无能为力——毕竟它刻意不碰 DTK 的身份池、不用
登录身份。打开 `HIDDEN_POST_CHECK_ENABLED` 后，会用作者的"发布总数"统计
（抖音自己维护的账号级计数，不受访客身份限制）当信号，核对 **预期总数** 与
**实际总数**：

| 观测 | 含义 | 处理 |
| --- | --- | --- |
| 实际 = 预期 | 账目对得上 | 什么都不做 |
| 实际 **>** 预期 | 有本地完全不知道的作品 | 用登录态身份核验一次，把它记为**对访客不可见**，并推送一条 `hidden_from_guest` |
| 实际 **<** 预期 | 有作品真没了 | 用登录态身份核验一次，确认是哪些不在了，按 `post_removed` 推送（**只判定落在这一次登录页窗口内**的作品：比窗口还旧的可能只是没出现在这一页，据此判删除会误报） |

**被标记为"对访客不可见"的作品，之后不再按游客视角判定它的消失**——因为对访客
来说它本来就看不到，再判一次只会得出错误结论。（这是必须记住的一件事：在游客
视角下，"真的被删了"和"只是访客看不到"长得一模一样，不记住核验结论就会每轮
重新判错。）它重新对访客可见时标记自动清掉。当作者把它**真删掉**时，总数会减少，
上表第三行会把它报成 `post_removed`。

核对只发生在五种时机：账号初始化 / 本轮有新作品 / 有作品被确认消失 / 长期无更新
兜底 / **低频保底**（`HIDDEN_CHECK_INTERVAL_MINUTES`，默认 30 分钟）。低频保底
是必需的：前四种都由游客视角的事件驱动，而"新作品从发布起就不可见"和"对访客
不可见的作品被删"这两件事**在游客视角完全不留痕迹**，只靠事件永远等不到它们。

默认关闭；配置项见[配置参考 · 隐藏作品核验](/config/reference#隐藏作品核验)。
定向核验需要一把带 `identity:manage` 的 Key 与一个登录态身份，见[权限 / API Key](/reference/permissions)。

## 置顶标志从哪来

DTK 的归一化结果不暴露置顶标志，只有 `include_raw=true` 时 `raw.is_top` 才有
值——**而且只有作品列表接口有效，详情接口的 `is_top` 恒为 0**。带 raw 会让响应
体积约 ×3，所以默认只在"发现新作品 / 标题变化 / 每 `RAW_REFRESH_ROUNDS` 轮"
时带一次，由 `INCLUDE_RAW` 控制（`auto` / `always` / `never`）。
